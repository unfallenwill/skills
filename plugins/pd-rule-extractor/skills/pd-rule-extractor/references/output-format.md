# 输出格式规范（严格固定）

最终交付物为一个 Excel 工作簿，含三个 sheet：**PD规则表**、**类别统计**、**说明**。sheet 名、列名、列序、取值字面量逐字遵循本文件，不得改动。由 `scripts/build_excel.py` 按本规范生成；阶段 3 编写 `rules-written.jsonl` 时即按本文件口径填写字段。

## Sheet 1：PD规则表

14 列，列序固定如下。一行一条规则。

| # | 列名 | 填写规范 |
|---|------|----------|
| 1 | 规则编号 | `PD-001` 起连续编号，三位数字，去重合并后统一分配，全表唯一、不重排、不留空洞 |
| 2 | PD类别 | 11 个固定类别字面量之一：入选排除 / 知情同意 / 访视 / 给药 / 样本采集 / 检查评估 / 合并用药 / 不良事件 / 随机盲法 / 试验药品 / 程序 |
| 3 | PD子类 | 简短名词短语（如"超窗访视""SAE 报告超时限"）；同类别下相同含义的子类用词保持一致 |
| 4 | 规则描述 | 一句话业务化描述"什么情形构成偏离"，面向临床数据管理人员可读 |
| 5 | 判定逻辑 | 可执行的条件表达式：含阈值、窗口、比较对象，用字段名引用数据点（如 `ICF日期 ≤ 首次给药日期`）。源文件给出具体数字必须保留；禁止使用"及时""适当""按规定"等无判据模糊词——源文件确实未量化时，照录原文表述并在备注注明"源文件未量化" |
| 6 | 相关访视 | 逗号分隔的访视名（以方案评估时间表为准）；全程适用写"所有访视"；不绑定访视留空 |
| 7 | 相关表单 | CRF 表单名（以数据库设计文件为准）；未知或不适用留空 |
| 8 | 相关字段/数据点 | 判定逻辑引用的字段名或数据点描述，逗号分隔 |
| 9 | 来源文件 | 来源文件名，不含路径；多来源用分号分隔 |
| 10 | 来源定位 | 定位锚点：docx 用 `§章节路径`、xlsx 用 `<Sheet>!R<行>`、pdf 用 `p.<页码>`；多处定位用分号分隔 |
| 11 | 原始规则编号 | 源文档自带的规则/条目编号（如 DVP 中的 check ID、方案条目号），多个用分号分隔；源文档无编号留空 |
| 12 | 严重程度 | 依 `.pd-extraction/severity-criteria.md` 判定填写（取值字面量以该文件为准）；源文档未定义判定标准则留空；配置 `severity_override` 时一律取覆盖值 |
| 13 | 重复规则指向 | 发生跨来源合并时，主规则本列记录被合并重复项的标识：有其原始规则编号用编号（如 DVP 的 check ID），无编号用 `来源文件:定位`；多个用分号分隔；未发生合并的规则本列留空 |
| 14 | 备注 | 见下方"备注列规范" |

### 备注列规范

备注为自由文本，多事项用分号连接。保留以下标准句式：

- 跨来源合并：主规则记 `N源合并`（N 为来源数，如 `3源合并`）。
- 审核未通过：`审核未通过：<理由摘要>`。**该句由 build_excel.py 依 review_status/review_notes 自动追加，写入方唯一**——阶段 4 回填时只把 fail 票理由的归纳（≤80 字）写入 review_notes，remarks 中不手写该句，避免双写。
- 源文件未量化：`源文件未量化，照录原文`。
- 引用外部手册：`细节引用外部手册：<手册名>`。
- 程序类规则：说明为何不能归入前十类。

## Sheet 2：类别统计

两列：`PD类别`、`规则数`。有规则的类别各占一行，按规则数降序排列（与参考格式一致）；规则数为 0 的类别不列。末行为 `合计`，规则数为全表规则总数（含审核未通过的规则）。

## Sheet 3：说明

键值两列（`项目`、`内容`），包含以下各行（具体行序以 build_excel.py 产出为准）：

1. **生成时间**：`YYYY-MM-DD HH:MM:SS` 格式时间戳。
2. **规则总数**：PD规则表行数。
3. **输入文件清单**：实际参与提取的文件名及识别类型（protocol/dvp/dbdesign）；缺类时明确写"未提供"。
4. **字段释义**：14 列逐列一句话释义（可用本文件表格的缩写版）。
5. **穷尽性证据**：
   - 覆盖矩阵统计：文档 × 类别矩阵中"产出规则格数 / 确认无格数 / 未覆盖格数（必须为 0）"。
   - DVP 对账结果：DVP 规则总数、已映射数、判定 non-pd 数、未映射数（必须为 0）。
   - 补提循环轮数：阶段 5 实际执行的轮数及收敛方式（连续两轮无新增），由主执行者通过 build_excel.py `--loop-rounds` 传入；未传入时该行写"未记录"。
   - 审核结果：通过数 / 未通过数。
6. **严重程度来源说明**：判定标准摘自哪个文件哪个定位；或"源文档未定义严重程度标准，该列留空"；或"由项目配置 severity_override 统一覆盖（详见 severity-criteria.md）"。该行由 build_excel.py 依 severity-criteria.md 内容自动判定（首行"未定义"→未定义；含 severity_override 声明→覆盖；否则→按项目文档定义）。

## 严重程度处理规则

1. 判定标准的唯一来源是 `.pd-extraction/severity-criteria.md`（阶段 0 从源文档提炼）。
2. 该文件记录"未定义"时，严重程度列整列留空，不臆造分级。
3. 该文件给出标准时，逐条规则对照标准判定，取值使用该标准自身的字面量（如 重要/一般、Major/Minor），不翻译不改写。
4. 配置 `severity_override`（非 null）时，忽略前两步，全部规则填覆盖值；同时主执行者把覆盖声明（"由项目配置 severity_override 统一覆盖为 <值>"）写入 `.pd-extraction/severity-criteria.md`，build_excel 依该文件生成说明 sheet 的严重程度来源行。
5. 单条规则对照标准仍无法判定时，留空并在备注注明 `严重程度无法依据现有标准判定`。

## JSONL 与列的映射

`rules-written.jsonl` 字段（snake_case）与 14 列一一对应，顺序如下：

```
rule_id          → 规则编号
category         → PD类别
subcategory      → PD子类
description      → 规则描述
condition        → 判定逻辑
visits           → 相关访视
forms            → 相关表单
fields           → 相关字段/数据点
source_files     → 来源文件
source_locator   → 来源定位
original_rule_ids→ 原始规则编号
severity         → 严重程度
duplicate_of     → 重复规则指向
remarks          → 备注
```

另有两个 JSONL 专属字段不进入 Excel 列，但由 build_excel.py 用于统计：`review_status`（passed/failed）、`review_notes`（3 票理由的汇总文本）。示例见 `examples/rules-written.example.jsonl`。
